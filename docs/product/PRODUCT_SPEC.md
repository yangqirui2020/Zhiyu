# Product Spec

## 核心定义

《知遇·一席》把知乎同一问题下的真实多元论证转成一间可探索的认知教室，并把用户笔记中的视角放回这间教室比较。它不替用户回答，只帮助用户看见：当前样本怎么想、我的笔记从哪里来、哪里可能值得我开口。

## 用户故事

当我面对一道有多种解释的知乎问题，我希望快速理解回答之间的论证结构；当我带入自己的学习笔记时，我希望系统只在有可核验证据时指出一个当前样本覆盖较少的切入角度，并让我回到知乎亲自表达。

## 四类角色

| 角色 | 表示什么 | 必须展示 | 绝不表示 |
|---|---|---|---|
| 学生 | 一条去人格化但保留出处的真实 `SourceContent` | 核心结论、理由、搜索摘要片段、原链 | Agent、匿名用户、正确性 |
| 课代表 | 一个观点簇的 AI 归纳 | 共同理由、代表来源、边界、固定署名 | 真实答主、知乎立场、通用聊天机器人 |
| 阿问 | 赛后长期 Persona | V1 最多低优先级“赛后见” | 伪造跨会话记忆、P0 入口 |
| Candidate Seat | 当前样本中可能值得贡献的个人视角 | 三项证据、分母、来源模式 | 全知乎知识空白、全新/正确观点 |

课代表 V1 冻结为静态 Inspector + 两个预计算、带 evidenceId 的示例推演：“回应另一簇的质疑”“追问本簇未覆盖的问题”。不提供自由输入框，不把预计算表演伪装成实时聊天。

## P0（6+1）

1. 备案问题 Classroom Snapshot。
2. Argument 抽取与可解释聚类资产。
3. Classroom 空间、学生/簇探索。
4. 笔记抽取 3–5 条 Claim。
5. Candidate Seat 三条件与证据 Inspector。
6. Live/Snapshot 统一 UI 与明确 provenance。
7. 闭环：三行提纲 + 去知乎问题页。

## P1 / Stretch

- 受控 Live Preview、更多备案题、真实 Provider smoke。
- 在 P0 全通过后，才考虑课代表自由聊天或任意题快速建室。

## Won't Do V1

- 网页抓取、回答全文假设、任意题稳定实时建室。
- 正确性、质量、支持率、权威度排名。
- 完整回答正文生成、自动发布、自动复制代写文本。
- 数据库、认证、多租户、社交、长期记忆。
- 多个学生 Agent、自由主题系统、Dify 与 Next 双主架构。

## Candidate Seat 规则

唯一合法 guard：

```text
与问题相关
AND 笔记中有明确表达/材料支撑
AND 当前样本覆盖较少
= candidate
```

任一维度为 `uncertain` 都不能亮座位。用户界面固定用：

- 与问题相关
- 来自你的笔记
- 当前覆盖较少

禁止使用“掌握”“新颖度”“知识空白”。固定披露：“基于当前检索到的 N 篇内容、X 个观点簇的对比”。N 必须按去重后的 source ID 计算。

## 数据与隐私承诺

- 证据若只有官方搜索摘要，必须称“搜索摘要片段”，不得称全文。
- 笔记是否发送第三方模型必须在提交前披露；不得宣称“仅本地解析”除非事实如此。
- 服务端不持久化笔记正文，不在日志中记录正文；只允许长度、hash、requestId。
- Reset 清除当前浏览器会话内的笔记、Claim 与 Candidate 结果。

## 成功标准

- 新用户在 3 秒内说出“这是一道问题下不同观点形成的教室”。
- 用户能解释一个学生为何属于某簇。
- 用户能核验 Candidate 的三项证据及真实分母。
- 用户知道系统没有证明“全知乎没人说过”，也没有代替自己写答案。
- Snapshot 断网路径能完整到达知乎 CTA。
